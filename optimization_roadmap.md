# Фінальне Технічне Завдання (Роадмап): Архітектурна Оптимізація AGREGAT

## Ввідні умови та цілі
- **Формат даних:** CSV (перехід на інші формати поки не планується).
- **Специфікація даних:** Level 1, таймфрейм **M1 (1 хвилина)**, об'єм — **Тіковий (Tick Volume)**.
- **Глибина історії:** До **30 років** (~11-12 мільйонів рядків на один торговий інструмент).
- **Ціль UI:** Швидкодія, плавність зуму та скролінгу має бути на рівні **TradingView** або вище.
- **Ціль Engine:** Здатність бектестера обробляти ці масиви за секунди/мілісекунди без фризів програми.

## Спринт 1: Data Pipeline & Memory Management (Обробка CSV)
*Звичайний `pandas.read_csv` для 11М рядків може споживати до 5-6 ГБ оперативної пам'яті і читатися хвилинами. Завдання цього спринту — миттєве завантаження та оптимізація RAM.*

### 1.1. Агресивний Downcasting (Зменшення пам'яті на 50%)
- При читанні файлу примусово встановлювати типи даних: 
  - `Open, High, Low, Close` -> `float32` (достатня точність для котирувань).
  - `Tick Volume` -> `int32` або `uint32`.
- Це зменшить вагу 11М рядків у пам'яті до ~1.2 ГБ.

### 1.2. Ліниве завантаження (Polars Lazy API)
- Заміна `pandas` на `polars`. Використання `polars.scan_csv()`.
- Дозволяє не завантажувати весь файл в RAM, якщо для розрахунків (або малювання) потрібен лише конкретний часовий проміжок (фільтрація відбувається ще на стадії читання з диска).

### 1.3. LRU Cache & RAM Pool
- Кешувати останні зчитані інструменти у пам'яті через `@lru_cache`, щоб при повторному відкритті графіка дані з'являлися миттєво.

## Спринт 2: Графічний Рушій "TradingView-Level" (UI Rendering)
*Малювання 11 мільйонів свічок звичайними методами PyQtGraph "вб'є" процесор. Потрібен кастомний рушій.*

### 2.1. Viewport Culling & Binary Search (Малюємо тільки те, що бачимо)
- **Технологія:** Відстежувати координати осі X (поточний екран користувача).
- **Оптимізація:** Використовувати `numpy.searchsorted` для блискавичного (0.0001 сек) пошуку індексів свічок, які потрапляють у видиму зону. 
- На відеокарту відправляються *лише* ці 500-1000 свічок, решта 11 мільйонів просто ігноруються рендерером.

### 2.2. Level-of-Detail (LOD Піраміда)
- Якщо користувач віддаляє графік так, що на екрані вміщається 10 років (всі 11М свічок), малювати хвилинки (M1) неможливо (ширина екрана ~2000 пікселів).
- **Алгоритм:** Динамічний ресемплінг. При сильному віддаленні графік "на льоту" (через Polars `group_by_dynamic`) перетворює M1 свічки на H1 (годинні), D1 (денні) або W1 (тижневі). Візуально графік не змінюється, але кількість макро-свічок падає до прийнятних 2000 шт.

### 2.3. C++ Batch Rendering (Кастомний Candlestick Item)
- Заборонити використання індивідуальних об'єктів для кожної свічки.
- Створити `FastCandlestickItem`, який використовує `QPainter.drawLines()` для малювання ВСІХ тіней одночасно, і `QPainter.drawRects()` для малювання ВСІХ тіл свічок за один виклик до GPU.
- Увімкнути `PySide6.QtOpenGL` для апаратного прискорення графіків.

## Спринт 3: Бектестер Високої Частоти (HFT-like Engine)
*Тестування стратегій бар-за-баром (у циклі `for`) на 30 роках історії займає непомірно багато часу.*

### 3.1. Numba JIT (Just-In-Time Compilation)
- Математичне ядро бектестера (відстеження профіту, збитку, виконання угод по цінах Open/Close) переписується на чистий NumPy і обгортається декоратором `@numba.njit`.
- Код компілюється в машинний LLVM код на льоту. Прохід по 11М рядках займатиме мілісекунди.

### 3.2. Векторизація генерації сигналів
- Логіка користувацьких стратегій (наприклад, перетин середніх ліній або власні умови) повинна розраховуватись векторизовано (без циклів, через масиви NumPy). Масив сигналів [Buy/Sell] генерується миттєво для всього датасету.

### 3.3. Multiprocessing Grid Search (Оптимізація)
- Для підбору ідеальних параметрів стратегії алгоритм розкидає сотні комбінацій параметрів на ізольовані процеси (`concurrent.futures.ProcessPoolExecutor`), завантажуючи всі 100% ядер процесора паралельно.

## Спринт 4: Неблокуюча Архітектура (Non-Blocking UI)

### 4.1. Worker Threads для Бектесту
- Жодних обчислень у головному потоці. Бектест стартує у фоновому `QThread`. Графічний інтерфейс не "замерзає", а відображає прогрес-бар та дозволяє клікати інші вкладки.

### 4.2. Асинхронний AI
- Всі виклики до LLM (OpenAI, Anthropic) для генерації коду стратегій виконуються через `asyncio` або фонові Worker-и зі статусом "Очікування відповіді мережі...". Це гарантує плавність платформи навіть при повільному інтернеті.
